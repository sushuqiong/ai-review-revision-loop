# 数据驱动手稿的"生成器纪律"与交付物完整性

> 来源：2026-09 EGFR 数据资源稿 v12→v14 全过程（外部审稿人与冷读 subagent 各抓到一次同类问题）。
> 适用：任何"数字从冻结表注入正文/表格/图件"的稿件（数据资源稿、队列研究、meta 分析）。

## 1. 生成器纪律（三个真实事故，全部由外部评审发现）

### 1.1 禁止按位置取值 —— 事故：TP53 被写成 0/96
- 现象：正文写 "TP53 reported in 0 samples (0.0%)"，两名审稿人据此判定"突变层 join 错位"（因为食管鳞癌 TP53 应 ~80–90%）。
- 真因：模板用了 `esc_mut[0]`（突变表首行恰为 KRAS 0/96）却标注成 TP53；**数据本身是对的（86/96）**。
- 铁律：所有跨表取值必须 **按键显式查找 + 断言唯一命中**：
  ```python
  def one(rows, **kw):
      hit=[r for r in rows if all(str(r.get(k,""))==str(v) for k,v in kw.items())]
      assert len(hit)==1, f"expected one row for {kw}, got {len(hit)}"
      return hit[0]
  tp53 = one(mut_rows, gene="TP53")
  ```
- 全项目排查同一模式（`[0]`、`head(1)`、`iloc[0]`、R 的 `df[1,]`）后再交付。

### 1.2 中位数必须先排序 —— 事故：median 报成 0.15（真值 0.33）
- 现象：正文 `median R² = 0.15 / VIF = 2.77`，随包表为 `0.33 / 2.09`，被两名审稿人独立发现。
- 真因：`x[len(x)//2]` 在**未排序**列表上取中间元素（恰为 GSE63089 的 0.145/2.773）。
- 铁律：一律 `statistics.median` / `statistics.quantiles`；交付前 grep 生成器里的 `len(` + `//2`、`np.median` 误用。

### 1.3 改生成器，不改产物 —— 事故：正文编辑被重建覆盖
- 现象：脚本 A 直接改写 `Manuscript.md`，随后脚本 B 从模板**重建**该文件 → A 的修改全部丢失（"manuscript updated: False"）。
- 铁律：单一数据源。任何文字/数字改动都落到**生成器**，然后重跑生成器；生成产物视作只读缓存。
- 交付前跑"数字 vs 表"审计：把期望出现的短语/数值列表逐条在正文里 grep，命中数不足即失败（见 `scripts/` 同类检查脚本思路）。

## 2. 交付物完整性（数据仓库式交付）

- **校验值两遍生成**：先冻结所有数据文件，**最后**写 `file_inventory_and_checksums.csv` 与 `checksums_sha256.txt`；两个校验文件**不写自身哈希**（写入 "self-reference" 说明），否则 `sha256sum -c` 必然 FAILED。
- **跨平台可校验**：清单用 **LF** 换行 + **正斜杠**路径（CRLF + 反斜杠会让 `sha256sum -c` 全部 "could not be read"）；README 写明 `rows` 列是"数据行（不含表头）"。
- **示例必须在构建时真跑**：示例脚本引用了已不存在的列（`beta_adj`）→ 审稿人一跑即报错；`expected_output/` 还是别的路径产出的旧文件。
  → 构建流程加一步：从包根运行每个示例 → 用示例自身输出**重新生成** `expected_output/` → 不一致即构建失败。
- **示例输入要"可命中"**：demo 矩阵若不含示例要用的基因（如 EGFR/ERBB2），GSVA/基因集匹配返回 0 命中、示例必失败；demo 应包含模块成员基因，并在零命中时 `stop()` 给出可读提示。输出带 `sample_id` 列。
- **包自足**：README/run_order 引用的每个文件必须真的在包里（曾引用不存在的 `cbio_v3_patient_module_scores.csv`、`figure_layout_qa.csv`、未随包的私有脚本）→ 要么随包发布，要么明确写"代码在 GitHub 仓库（附 commit/DOI）"。
- **完备性枚举**：声明"完整估计层"就要求 `队列数 × 模块数 = 行数`；缺口行必须以 `not estimable + 原因` 保留（本项目 26×17=442 = 434 估计 + 8 不可估计）。审稿人一定会算这个乘法。
- **"精确复现"必须给容差**：不要写 "absolute difference = 0"，改写"在预设容差 1e-6 内复现（观测差 0）"，并说明复算用的是**同一处理矩阵**而非重新下载；秩一致（Spearman 0.95–0.98）单独表述，绝不写成 reproduction。

## 3. 一句话清单（每次交付前）
1 有无按位置取值？ 2 中位数排序了吗？ 3 改的是生成器吗？ 4 `sha256sum -c` 是否 0 个非 OK 行？ 5 示例是否真跑过且期望输出同源？ 6 被引用的文件是否都存在？ 7 行数是否等于枚举乘积？ 8 是否给了预设容差？
