# 批量编辑与构建链安全（血泪教训）

来源：课题2 v12–v19。**同一个错误类在这次投稿周期里犯了三次，每次都改坏了已交付文件。**
发布任何批量编辑前，先读这一页。

## 一、过度宽泛的全局替换（最常犯）

### 实例 1：`2,056` → `2,092` 把判别样本一起改了

**背景**：为保证 L 层口径统一，脚本里写了
`L_PAIRS = [("2,056", "2,092"), ...]` 之类的**无上下文替换**。

**后果**：稿子里有两类 2056/2092：
- **关联样本** = 2,092（且被误写成 2,056 → 应改成 2,092）
- **判别样本（要求腰围完整）** = **2,056，本来就该是 2,056！**

无差别替换把**判别样本也改成了 2,092**，与同句中"the waist-complete subset"自相矛盾，且与图 1 冲突。
更糟的是：从中期备份恢复时**把这个错误又带了回来**，需二次修复。

**根因**：同一数字在不同语境下有**不同正确值**。

### 实例 2：在"第一个句号"处插引用，插进了小数中间

**做法**：脚本按"找到关键词后的第一个 `.` 然后插入 `(Table S11)`"。

**后果**：目标词后面紧跟的是数字 `0.826`，句号在数字中间 —— 结果生成
`the M4 per-SD OR was 0 (Table S11).826 (0.688–0.991; P=0.041)`。

### 实例 3：同类问题反复出现

复审时又发现"只改了前半个分句"：同一段里
`gives 1.018 on the own-SD scale and 1.020 on the common-increment scale — the quantity reported as 1.012 and 1.014 in Panel B of Table 6`
—— 前半句改成 1.012 了，**后半句的 1.020 还在**，一句话内自相矛盾。

---

### 安全规则（发布任何批量编辑前逐条过）

1. **不用无上下文替换**。替换必须带**足够的左右锚点**，让匹配唯一。
   ```python
   # ✗ 危险
   s.replace("2,056", "2,092")
   # ✓ 安全：带语境
   s.replace("Discrimination samples: n = 2,846 (296 dx), 2,056 (232 dx)",
             "Discrimination samples: n = 2,846 (296 dx), 2,056 (232 dx)")   # 本就不该改
   ```
2. **替换前先 `grep -c` 出全部命中，逐条判语境**。数量对不上就停手。
3. **不在"第一个句号/逗号"处插文本** —— 用**完整句子锚点**或**段落级替换**。
4. **改完立刻复查同段落**：同一段内是否还有同类旧值残留（实例 3 就是这么漏的）。
5. **恢复备份前先想清楚**：备份是"某次修改之前"的状态，**可能含已修好的旧错误**。
   从备份恢复 = 回退到该时点，**之后的所有修复都会丢失**。
6. **每轮改完跑一次"残留串清单"**：把"应已消失"的字符串列成清单逐个确认归零，例如
   `["0.974", "0.588", "1.752", "1.018", "1.020", "caliber", "Guozhen", "analysis code"]`。

## 二、构建脚本覆盖已交付手稿

### 事故

主稿 `manuscript.docx` 是**在 docx 上做 run 级定点编辑**产出的（用户已手工重命名/清理过）。
后来为了核查词数，运行了 `_build_docx_v18.py` —— 该脚本的**内容模块 `_ms_content_v18.py` 已过期**
（停留在打包前：摘要 342 词 / 8 表），于是**把交付稿整份覆盖成旧版**，丢掉了：
摘要压缩（299 词）、Table 8 → S13、引用顺序修复、Cover letter 更新。

### 恢复路径（已验证）

```
① 从 _bak/v18_pre_bmc/ 恢复 5 份 docx
② 重跑可直接重入的打包脚本（_v18_bmc_pack.py）
③ 重跑引用归位 + Cover letter 完善
④ 全面终验
```

### 规则

1. **只要稿子经过"docx 上定点编辑"，构建链就与交付稿脱钩** —— 此时**禁止再运行构建脚本**。
2. 在 README 里**显式写明**："`<构建脚本>` 已与交付稿不同步，除非要重建，否则不要运行"。
3. 若确需重建，按**「恢复 → 打包 → 归位 → 校验」**四步顺序，**每一步后校验**。
4. **清理临时文件时不要切断构建链的 import 依赖**：一次清理把 `_ms_content_v1{5,6,7}.py` 移进 `_bak/`，
   导致 `_ms_content_v18.py` 无法 import —— 这正是我后来图省事直接跑旧脚本的诱因。
   清理前先 `grep -l "import _"` 确认没有模块被别的脚本依赖。

## 三、编辑 docx 的通用纪律

- **段落多为单 run**：整段替换用 `p.runs[0].text = new; for r in p.runs[1:]: r.text = ""`
- **绝不**用 `write_file` 写回 `read_file` 的内容（`LINE_NUM|` 前缀会写进文件）—— 用 `patch` 或 Python
- **改前必备份到 `_bak/`**，备份名带语义前缀（`v19d_pre_avail.docx` 而非 `backup1.docx`）
- **数值零改动校验**：任何"只改文字"的批处理，都要比对 `table cell.text` 列表与正文数字 token 改前↔改后一致
- **中文残留**：`len(re.findall(r"[\u4e00-\u9fff]", text))` 应为 0（投稿文件）
- **改完的终验清单**：段数 / 表数 / 文献编号连续 / 引用首现序无逆序 / S 编号全覆盖 / 占位符 0 / 双空格 0 / 断句
