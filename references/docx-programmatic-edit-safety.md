# 程序化改 docx 的安全守则 (Programmatic docx-edit safety)

## 何时用
用 python-docx 批量修改已定稿手稿时：删内嵌表、重映射补充材料编号（S1–S8 → S1–S9）、
批量换数字、调词数、重嵌图。**这类操作极易引入新缺陷**——实测一轮批量编辑引入 8 处硬伤，
全部被随后的独立对抗审查抓到，且都是"一眼可见"级别。

---

## 一、实测血泪清单（本轮 15 项问题中 8 项由自己的批量编辑造成）

| # | 操作 | 引入的缺陷 |
|---|------|-----------|
| 1 | 删主稿内嵌的 4 张补充表 | 表删了、**标题段没删** → 孤立空标题 "Supplementary tables"（其下无内容，紧接 "Figure legends"）|
| 2 | S 编号重映射 | 正文出现**悬空引用** "Table 2, Panel B"（该处内容实为 Table S5，重映射时漏改/错指）|

| 4 | 生成内容模块 | 长字符串跨行拼接 → 生成的 `_ms_content_v15.py` **语法损坏**（4 处 `NAME = "…"` 未闭合，连修 3 轮耗尽预算）|
| 5 | 改 ylim / 字号 / 加图号标题 | 重制图后**未重新嵌入** → docx 里仍是旧图（且 v15 主稿一度只有图注、0 内嵌图）|

## 二、铁律

### (1) 任何批量编辑后，必须跑一次交叉引用与一致性扫描
- **声明段列的 S 编号 ↔ 正文实际引用 ↔ 独立补充材料实际表号**，三方对齐
- 每个 `Table Sn / Figure Sn` 引用都能找到落点；每张表/图都在正文被引用（**孤儿要补插引用**，别只留在声明里）
- 表号、图号连续；无空标题段；无断句残缺段（删改易把句子拦腰截断）
- **计数类声明**（表数/图数/文献数/词数）与实测一致
- 删除操作要连带其"附属段"（表 → 表题 + 表注 + 可能的 panel 标题）

### (2) 优先"内容模块重建"，不要事后打补丁
- 打补丁 = **交付稿与生成代码脱钩** → 违反"代码可复现"承诺，审稿人会要求提供生成代码（GPT6 明确提出过"投稿前应提供可核验的补充材料"）
- 正确链路：`_extract_*_content.py` 从**交付稿反向抽取** → 生成内容模块 → 改内容模块 → 构建脚本重新生成 docx
- **抽取器写长字符串必须用 `repr(值)` 单行输出**，不要手工拼接跨行字符串
- 重建后逐段比对"重建稿 vs 交付稿备份"的**段落文本序列 + 表单元格文本**，差异数应为 0

### (2b) 内容模块重建链的四类实测坑（本轮全部踩过并修好）

**坑 1 — 生成的 Python 模块语法损坏：长字符串跨行**
`lit(text, indent=N, width=96)` 这类"带缩进换行"的写出器产出的是
`NAME = "第一段"\n        "第二段"` —— **这不是合法的 Python**（第二行无运算符）。
- ✗ 错解：手工把续行合并成一行（正则会误伤模块三引号 docstring，越修越坏）
- ✓ 正解：**用括号包裹实现隐式拼接** ——
  `A("NAME = (" + lit(text, indent=N, width=96) + ")")`
  产出 `NAME = ("第一段"\n        "第二段")`，合法且保留可读缩进
- 修完立刻 `ast.parse()` 验证，**每次只改一类**（5 个头部变量 + SUPPLEMENTARY 共 6 处）
- 不要把 `repr()` 当作万能解：对已被 `textwrap` 折行的文本，括号法才是最小改动

**坑 2 — 构建器重复/丢失表标题**
`tabtitle` 块与 `table` 块**都调用 `add_table_title()`** → 标题出现两次；
把 `table` 分支里的调用删掉后若 `tabtitle` 分支本身没生效 → 标题**完全消失**。
- 判别方法：直接数 `[p for p in paras if p.text.strip().startswith("Table ")]`，
  期望值 = 表数；出现 2×表数 = 重复，0 = 全丢
- 先确认 `tabtitle` 块真的被渲染，再删 `table` 分支的重复调用

**坑 3 — 校验脚本把自己的"基准备份"覆盖掉（会骗过自己）**
`verify_rebuild.py` 若开头写 `shutil.copy2(MAIN, BAK)`，**第二次运行时 MAIN 已是上次的重建稿**
→ BAK 变成重建稿 → 比对"重建 vs 重建" → 必然 0 差异，**假通过**。
- ✓ 铁律：基准备份只在**任何编辑之前**做一次，命名为 `_bak_main_vN_final.docx` 并**永不被脚本覆盖**
- 两个性质要分开验：
  (a) **保真性** = 重建稿 vs **真原始备份**（应只剩本轮有意的文字增删）
  (b) **幂等性** = 重建稿 vs 再重建稿（应为 0 差异，证明构建确定性）
- 比对用 `difflib.SequenceMatcher` 看 opcodes，不要只看总差异数——能一眼分辨"空行位移"与"内容丢失"

**坑 4 — 文档重构后校验脚本的期望值全面过期**
把内嵌补充表迁出主稿后，`_verify_*.py` 仍在找 `C.SUPP_TABLES`（已不存在）→ AttributeError；
词数阈值也需随压缩目标调整。
- 重构后**必须重新跑一遍校验脚本**，逐条判断 FAIL 是"文档真错"还是"脚本期望过期"，
  两者处理方式完全不同（改文档 vs 改脚本）
- 指向补充材料内容的检查项，应改为**读独立补充材料 docx**，或从主稿校验器中移除

**坑 5 — 重建链**不幂等**：表后空段被双计（v16 实测，最隐蔽的一坑）**

现象：重建稿**每跑一轮多出 7 个空段**（185 → 192 → 199…），非空段数却始终一致，
所以只看内容的比对完全看不出来。

根因（链的两端各做一次）：
- **构建端**：`add_booktabs_table()` 在**每张表后自动加 1 个空段** → 7 表 = +7
- **抽取端**：抽取器把交付稿里这些空段当成 `('spacer', None)` **收进 BODY**
  → 下一轮构建又补一次 ⇒ 每次往返净增 = 表数

✓ 修法（改抽取端，一处即可）：**跳过紧跟 `table` / `tabfoot` 块的空段**
```python
elif kind == "spacer":
    if BODY and BODY[-1][0] in ("table", "tabfoot"):
        pass                      # 由构建端自动生成, 不重复计入
    else:
        BODY.append(("spacer", None))
```
修后实测：`171 → 171 → 171`（全段数），幂等成立。

✓ 验证脚本必须同时报**三个数**，缺一即会**假通过**：
```python
print("非空段", len([p for p in d.paragraphs if p.text.strip()]),   # 内容
      "全段",  len(d.paragraphs),                                   # 空段漂移
      "表",    len(d.tables))
```
> 反面教材：本项目 `_verify_v*_rebuild.py` 最初**只比对非空段与表**，
> 因此对空段膨胀**注定永远输出 ✅**。审查者用独立重跑才把它证伪。
> ⇒ 凡自写的"可复现性"校验，先问一句：**它能检测出我已知的失败模式吗？**

**坑 6 — 「可完整重建」这类强声明，必须由**独立方重跑**后才敢说**

本项目父代理曾据自写校验器宣布「代码可完整重建交付稿」，被独立审查者重跑后**证伪**
（多 7 空段、且不幂等）。教训：
- subagent / 自己写的校验器输出**不是验证**；强声明要交给**未参与编辑的一方**去重跑
- 把这条明确写进审查指令：**"请独立重跑该链并自行比对，勿只读结论"**
- 顺带：`_ref` 基准备份若在每轮开头被覆盖，就会退化成本轮产物的副本，
  比对变成"重建 vs 重建" ⇒ 见坑 3

### (3) 图表与正文必须共用单一数据源
- 图脚本里 **禁止硬编码 override 字典**。实测：
  `override = {("N3","dx_nosx"): (2.506, 1.710, 3.672)}` 把**错值**传播进正文；
  权威值实为 `2.518 / 1.715 / 3.698`（独立重跑确认）
- 正确做法：图脚本只读权威 TSV/RDS；脚本内加断言，把主稿表值逐行比对，不一致即 FAIL
- **舍入必须同档**：图内值 = 表内值（同一舍入规则）。1.995 vs 1.996、1.623 vs 1.624 这类
  0.001 差异会被审稿人当"图-表不符"抓出来

### (4) 词数口径必须一次锁定并写死
同一篇稿的三种口径差得很多（实测）：

| 口径 | 摘要 | 正文 |
|------|------|------|
| 不含结构标签 / 纯叙述 | 300 | 7,859 |
| 含结构标签 / 含表注 | 304 | 9,627 |

- 锁定**一个**口径，在 Title page **明写口径**，README 与 docx 同步
- 用整篇扫描统计（界定起止段：`1. Introduction` → `References`），**不要只对某几段求和**
- 别让校验脚本把错误期望值"固定下来"（本轮 `_verify_v15_package.py` 曾把 "Tables: 11" 写成期望值）

### (5) 改完必须重新嵌入并复核
- 图文件重制后务必**重嵌 docx**：删旧图片段 → 重插 → 核对内嵌图数量与顺序
- 清理**孤儿 media**（zip 层删未引用的 `word/media/imageN.png` + 对应 `document.xml.rels` 条目）
- 图内标题与正文图号一致（本轮 Fig1/Fig2 的 PDF 内曾缺 "Figure N." 标题，Fig3 有）

### (6) 行内引用的自动插入：锚点规则 + 插后正则扫描

把 `(Figure S1)` / `(Table S7)` 这类行内引用**自动插进已有句子**时，
绝不能用「关键词后第一个句点」当锚点——**小数点也是句点**。

- ✓ 正确锚点：**从句/句末位置**插入，或直接改写成独立从句；
  更稳的做法是**手工确认落点**（这类插入每篇不过 3–5 处，不值得自动化）。
- ✓ **插后必扫**（正则必须**同时覆盖 Figure 与 Table**，命中即回退修）：
  ```python
  # 注意: 早期版本只写 Figure, 于是 Table 类的复发被漏掉(见下方 v18 实例)
  re.search(r'\d\s*\((?:Figure|Table) S\d', full)   # 数字紧跟左括号 → 多半插进了小数
  re.search(r'\((?:Figure|Table) S\d\)\.\d', full)  # 右括号紧跟小数 → 同上
  ```
- ⚠ **v18 实测复发（说明"写进守则"不等于"不会重犯"）**：
  插入规则换成「关键词后**第一个句点**处插入 `(Table S11)`」——同一个根因（**小数点也是句点**），
  但引用类型变成了 Table，而当时的扫描正则只覆盖 Figure ⇒ **漏检**，产出
  `the M4 per-SD OR was 0 (Table S11).826 (0.688–0.991; P=0.041)`，被审查者当"稿未经校对"抓出。
  - ⇒ 教训 1：**扫描正则要按"引用类型"取并集**（`Figure|Table`），不要只写当前在用的那一种。
  - ⇒ 教训 2：**插入位置的安全写法**是挂在**数值短语之后**，不要挂在数值内部：
    ✓ `0.826 (0.688–0.991; P=0.041) (Table S11)`　✗ `0 (Table S11).826`
    实操上**每处手工确认**（每篇不过 3–5 处），比反复调试锚点规则更省时。
- ✓ 同时检查**引用编号本身**：`[41,4]` 这类乱序（应为 `[4,41]`）——自动插入很容易破坏升序。

### (7) 生成式「文件清单」必须映射成投稿中性名

只要稿件里有「随稿提供的文件」清单（Availability / Data & Code availability / Declarations），
**不能用工作目录的真名去填**。

- ✗ 实测泄漏：`01_数据/`、`02_复现代码/`、`04_投稿材料/`、`v16_A_ipw_full.R`、`_make_figs_v16.py`
  → 英文稿件里出现中文目录名 + 内部版本串 + 下划线前缀脚本名。
- ✓ 做法：维护一张映射表，生成时替换为投稿中性名：
  `01_数据/`→`data/`、`02_复现代码/`→`code/`、`vN_A_ipw_full.R`→`ipw_full.R`、
  `_make_figs_v16.py`→`make_figures.py`。
- ✓ 并**断言正文无 `_` 前缀脚本名、无版本串（v14/v15/v16）、无数据目录名**。
- ✓ 若确实要随稿提交代码，**把副本按中性名重命名后再打包**，让清单与实际文件一致。

### (8) 扫描报警后要看**整段**，不要看截断片段

实测：CJK 扫描报「中文 36」，但打印前 220 字符的片段**看起来完全干净**——
中文在长段的后半部分（`Availability` 段末尾的文件清单里）。
⇒ 凡扫描命中，**打印整段或把命中位置前后各 200 字符一并输出**，否则会误判为误报而放过。

### (9) 自写校验器也会**误报**——先分清"文档真错"还是"检查口径错"（v17 新增）

批量编辑后自跑的扫描器，命中不等于缺陷。本轮实测两类误报，处理方式与真错**完全不同**：

| 报警 | 真相 | 处理 |
|---|---|---|
| 「[24] 与 [25] 重复」| 两条 NCHS 文献**前 80 字符相同**（同一机构的不同周期数据集），**并非重复** | **改检查器**：按完整标题/DOI 去重，不要按前缀 |
| 「PIR 缺失数 482/337/668 在主稿缺失」| 这些明细**本就应在补充材料**（主稿只给一句） | **改检查器**：指向补充材料内容，或从主稿校验器移除 |
| 「FigureS1–S3_v17 缺失」| 图文件仍是 `_v16` 命名，内容可用 | **改文档**：统一重命名到当前版本号 |
| 「正文词数 9,711 > 7,000」| 我的口径把表注/图注都算进了"正文" | **改检查器**：锁定与 Title page 相同的口径 |

⇒ 铁律：**扫描命中后，第一问是"这是文档的问题还是我的检查口径的问题"**。
- 每条 FAIL 都要能解释成"文档真错"或"脚本期望过期"，二者不可混为一谈（与坑 4 同源）。
- 反过来同样成立：**校验器报 ✅ 也可能是假通过**（见坑 3、坑 5）——
  所以校验器要有**已知失败模式**的回归意识，并交给**未参与编辑的一方**独立重跑。
- 实践结论：**跑完扫描不要只报"未通过 N 项"，要逐项给"真错 / 口径错"的判定**
  （本项目终验即按此把 5 项报警收敛为 0 真错）。

### (10) 残留扫描的 token 清单必须在**最后一次内容新增之后**重建（v18 新增）

**症状**：同一份补充材料里，两张表对**同一层**给出互相矛盾的数（Table S3 Panel C：样本 2,092 /
ESS 1,290 / M3 1.425；新增的 Table S12：2,056 / 1,271 / 1.415），而正文**混用两套**
（计数取 2,092、OR/ESS/权重取 2,056）。扫描当时**没报**，因为它不在 token 清单里。

**根因（两个叠加，值得单独记）**：

1. **分析脚本被"复制前移"时会静默继承旧样本口径。**
   本轮新增的"五种缺失设定敏感性"脚本是从 `v16_A_ipw_full.R` / `v17_A_ipw_v2.R`
   **复制改写的**，而那两个脚本建在**腰围完整 L=2,056** 上；可上一轮已把主关联样本及其
   对应表改成 **2,092**。⇒ **新脚本不会自动跟随口径变更**，它跟随的是**它被复制来的那一刻**。
   通用判据：**"本轮新增的分析"与"上一轮改过口径的表"是两个独立演化的事物 —— 必须显式对齐。**

2. **token 清单是"上一轮写的"，而冲突内容是"这一轮才加的"。**
   扫描清单只覆盖了当时已知的旧值（`0.8125` 之类），**新表带来的新矛盾形式不在其中**。

**✓ 铁律**：

```
[ ] 只要本轮**新增了任何表/段**，就**重新生成本轮的 token 清单** —— 从当前 docx 列举
    "本应互相一致的那些量"，而不是沿用上一轮的记忆清单。
[ ] 口径类变更后，**枚举所有报告该层的表与段**（主稿 + 补充材料的每一张表），逐一确认来源；
    不要假设"新脚本必然用了新口径"。
[ ] 为每个口径锚点同时断言**两种值都不能出现**：
    该出现的新值（2,092 / 1,425 / 1,290）在 → OK；该消失的旧值（2,056 / 1,415 / 1,271）在 → FAIL。
    只断言"新值在"会漏掉"旧值也还在"这种共存型矛盾。
[ ] 同一份文件内**跨表交叉核对同一量**（表 vs 表），不只做"表 vs 正文"。
```

**报告规范（顺带固化为写作要求）**：凡涉及样本流失的分析，**显式给三个计数**——
**目标人群 / 实际进入模型 / 最终分析样本**，并说明"因预测变量缺失再减员多少"。
本轮正是靠这三个数才把矛盾定位清楚；反之，只说"分析样本 n=2092"就无法暴露中间环节的错位。

### (11) 一个数字承载两种含义时，**禁止全局替换**（v18 实测，审稿人必抓）

**症状**：把某层样本口径从 2,056 改为 2,092 时，用 `L_PAIRS` 里一条
`("2,056", "2,092")` 做**全局替换** → 正文出现**自相矛盾**的表述：

> Discrimination samples: n = 2,846 (296 dx), **2,092 (232 dx; the waist-complete subset of
> the 2,092-participant L-series association sample)**, and 5,724 (438 dx)

括号自己说"waist-complete subset"，数字却是 2,092——**因为 2,056 在同一篇稿里同时是两件事**：

| 数值 | 旧口径下的含义 | 新口径下的含义 |
|---|---|---|
| **2,056** | 关联样本（要求腰围完整）| **判别样本**（腰围完整是 LAP 比较的硬条件，**合法保留**）|
| **2,092** | — | **关联样本**（去掉腰围要求后 +36 人）|

⇒ 全局替换**把该保留的 2,056 一并改掉**，消灭了"关联样本 / 判别样本"的区分。

**✓ 铁律：任何"一个数字 → 另一个数字"的批量替换前，先枚举并分类，再只改目标类。**

```python
# 1) 先只列举，不改写
for i, p in enumerate(doc.paragraphs):
    for m in re.finditer(r'2,056', p.text):
        print(i, '...', p.text[max(0,m.start()-120):m.start()+80], '...')
# 2) 按上下文关键词分类: association / discrimination / waist-complete / LAP / sensitivity
# 3) 只替换目标类，且**逐条手写**完整锚点串（含前后语境），不要写裸数字对
```

**通用判据**：一个数字若在同一文档内被用于**两个不同的量**（不同人群、不同子集、
不同口径），它就**不能**作为批量替换的 key。判据是问一句：
**"这个数在稿中是否只表示一件事？"** 答不上来就先枚举。

**同源症状（同一轮的另一处）**：`2,092 (232 dx)` 与 `2,056 (232 dx)` 的 **dx 例数相同**（232）
本身就是一个信号——判别样本是关联样本的**子集**，例数可以相同，但人数必须 ≤。
凡看到"子集人数 ≥ 全样本人数"或"两处 n 相同而定义不同"，先停下核查。

### (12) 必填声明项的扫描器要容忍**弯引号**（v18 实测假阴性）

BMC/多数期刊要求 Declarations 含 `Authors' contributions`。用直引号串
`"Authors' contributions"` 去 `in` 判断会**漏检**——docx 里通常写作
**`Authors’ contributions`**（U+2019 直角撇号 `’`，不是 U+0027 `'`），
于是脚本报"缺失"，而实际段落里明明有。

⇒ 扫描必填项时**两种撇号都试**（或先做
`text.replace("\u2019", "'").replace("\u2018", "'")` 归一化再匹配）；
同理 `≠`、`–`/`—`、`≥` 等排版字符也应在归一化后再比对。
**假阴性比假阳性更危险**：它让你去"补"一个已经存在的声明，从而**制造重复段**。

### (13) 「编辑是否真的生效」——patch 空操作会触发 File-mutation verifier 警告（v18 实测，用户会追问）

**现象**：回合结束时出现
`⚠️ File-mutation verifier: 1 file(s) were NOT modified this turn despite any wording above that may suggest otherwise. • <path> — [patch] old_string and new_string are identical`。
用户会直接拿这条来问「为什么报警」。

**根因（不是 bug，是设计）**：当 `patch` 的 `old_string` 与 `new_string` **完全相同**时，工具**拒绝执行**
（返回 `identical` 错误），文件字节不变；而我在同一回合的文字里说了\"已修复该脚本\"，
回合末的文件变更校验器因此如实提示\"措辞暗示有改动，但该文件本回合未被修改\"。

**✓ 铁律**
```
[ ] 发 patch 前自检 old_string != new_string；相同即不要再发（空操作必然留警告）。
[ ] 需要\"重写某段/整文件\"时用 write_file；patch 只用于真正的差异替换。
[ ] 报\"已修复\"之前先确认工具返回 success=true 且 diff 非空——不要把\"重新表述\"当成\"已修改\"。
[ ] 被追问该警告时，用证据回答而不是复述警告文本：
      git status --porcelain（干净 ⇒ 无未落盘改动）
      ls -la <文件> + read_file/关键词计数（确认文件现状与产物时间戳）
      然后解释：（a）该 patch 是空操作被工具拒绝；（b）真正的修改随后由 write_file/另一脚本完成；
      （c）警告只说明\"本回合未改该文件\"，不等于\"任务未完成\"。
```
**为何值得记**：这条警告极易被误读成\"任务失败/文件损坏\"，而实际语义是\"该文件本回合没动\"。
先分清\"工具拒绝空操作\"与\"任务没做完\"，再决定是否需要补救——本项目两种情形都出现过，
区别办法就是 `git status` + 产物时间戳。

**同源教训：不要用截断的输出判断\"文件/目录丢失\"。**
实测 `ls -la <两个目录> | head -6` 把第二个目录的条目切掉，我据此报\"06_投稿清单与流程 为空\"——
实际文件存在，只是被 `head` 截断。凡\"目录为空/文件缺失\"这类结论，
必须用**存在性检查或计数**（`os.path.exists`、`len(os.listdir)`、`ls | wc -l`）来支撑，
不要从截断的列表里推断。
