# 已被用户手改过的交付文件：定点修 + 变更标蓝（最高风险窗口）

交付之后用户会**自己重命名、自己动手改**。这个窗口里最危险的动作是"重跑构建脚本"。

## 一、铁律：用户动过的文件，绝不重跑构建脚本

实测发生的事（JCEH-D-XX-XXXXX 返修轮）：
1. 用户把交付文件重命名：`01_Manuscript_JCEH_revised.docx` → `Manuscript_revised.docx`、
   `02_...` → `Point-by-point response.docx`、`03_...` → `Title_Page_revised.docx`、
   `07_...` → `Figure_Legends_revised.docx`；
2. 又跑了一次全局"特殊字符 → ASCII"清理（en dash `–` → `-`、直引号 → 弯引号、
   **全部 Unicode 上标被清掉**）；
3. 还删掉了手稿末尾的 Figure legends 整节。

此时若用生成脚本（`44_revise_manuscript_v2.py` 等）重出文件，会**从 pristine 原件重建**，
把上面三项用户改动**全部悄悄抹掉**（en dash 回来、上标回来、删掉的节回来、字数回到旧值）。
用户不会立刻发现，但这是最难解释的一类错误。

**正确做法：在用户当前文件上做定点（run 级）修改。**

```python
from docx import Document
doc = Document(user_path)
for par in doc.paragraphs:
    for r in par.runs:
        if OLD in r.text:
            r.text = r.text.replace(OLD, NEW, 1)      # 只动这一个 run
            break
doc.save(user_path)
```
- 只改目标 run，其余 run、格式、节结构、用户的其它改动**一律不动**。
- 改完**回读整句**确认（本轮回读抓到两处标点滑落：`= 0.004)` 丢了右括号；
  `), Supplementary Fig.` 应为 `); Supplementary Fig.`）。
- 每条替换都要 **assert 命中**（`assert OLD in run.text` 或打印 OK/MISS），
  否则静默漏改。

### 反面教材：整段 `set_text(p, 新全文)` 会压平上标
手稿的引用编号是**独立的上标 run**。用整段重写（`runs[0].text = 新全文` + 删其它 run）会把
所有 run 合并成一个，**引用上标全部变成普通文字**。本轮真实命中：重建手稿时一处整段替换
让引用 13 从"上标 13"变成"正文 13"（引用完整性检查随后报"1..54 缺 13"）。
⇒ 若确实需要整段替换，**必须在"引用→上标"转换之前做**；转换永远放最后一步。

## 二、要建"对照版"时，把输出重定向到草稿目录

想 diff 出"用户改了什么"，需要一份自己版本的副本。做法：
```python
src = open(build_script).read()
src = src.replace(r'OUT = r"C:\Users\fengq\Desktop\<交付目录>', r'OUT = r"...\_ref')   # 前缀替换
```
**坑**：脚本里 `OUT` 的定义可能含文件名（`OUT = r"...\<交付目录>\01_Manuscript_....docx"`），
用"目录"做前缀替换会**替换失败但脚本照跑**，于是**直接在用户的交付目录里生成了一个新文件**。
- 替换后必须 `assert PREFIX in src`。
- 跑完先 `ls` 交付目录，确认条目数与动手前一致；发现多出来的文件立刻删掉并如实告知用户
  （"检查过程中误建过一个文件，已删除，目录已复原"）。

## 三、动手前先备份，动完用 diff 自证

```python
shutil.copytree(delivery_dir, "_backup_before_fix")
```
改完跑 `difflib.SequenceMatcher` 逐段对比 backup vs 现文件，把**完整差异清单**贴给用户
（"只改了这 4 处，其余一字未动"）。这是"没引进新错误"的唯一可信证明。

## 四、用户全局清理的两个连带后果（每次都要复检）

1. **科学计数法上标被吃**：`P = 1 × 10⁻⁴` → `1 × 10-4`、`2.9 × 10⁻⁷` → `10-7`
   （本轮命中 3 处：手稿 1 + 回复信 2）。
   ⇒ 用户清理后 `grep -E "10\s?-\s?\d"`，恢复上标或写 `10^(-4)`。
2. **字数漂移**：清理会加/减词（本轮 +1 词），而标题页的字数是**派生值**。
   ⇒ 任何文字改动之后**重算字数再写标题页**；删掉一个 17 词的从句后，标题页必须从
   5,562 改成 5,545。永远"数字跟着正文走"，不要反过来。

## 五、变更标蓝（用户会主动要）

用户原话："做了改动和增加文字的地方，全部改用蓝色字体标出来，方便我核对"。

**不要用 diff 猜**。试过基于 `difflib` 的词级 diff + run 拆分，在引用密集的段上大量误标
（引用编号从 `[1]` 变上标后每个编号都被判为"新增"，54 条参考文献的编号全变蓝），
且段落对齐会被引用格式差异带偏。

**用确定性的源级标记**（脚本与要点见 `scripts/` 同级说明，实现如下）：
1. 在构建/修补文本时，把**新增或改写的片段**用私用区字符包起来：
   `O = "\ue000"`、`C = "\ue001"`（正文里不可能出现的字符）。
2. 生成后跑一次后处理：扫描每个 run，把标记之间的片段拆成独立 run 并
   `run.font.color.rgb = RGBColor(0,0,255)`，同时**删掉标记字符**。
3. 用一个环境变量开关产出两份：`NO_BLUE=1` → 干净的投稿版；默认 → 蓝标核对版。
   两份**逐字相同**，只是颜色不同（本轮实测：正文文字完全一致、0 处残留标记字符）。

标蓝的三条口径（要主动告诉用户）：
- **全篇统一的格式转换不标蓝**（如引用 `[1]` → 上标、参考文献 `[1]` → `1.`）——
  逐处标蓝会淹没真正的内容改动，且版面上已能一眼区分。做法：diff 前先归一化掉
  `\[\d+\]` 与行首 `\d+\. `。
- **按段落整段标蓝**（不是逐词），便于用户定位"需要重读的段落"。
- 标蓝版**不能投稿**：同时生成 `投稿用_去蓝标版本/` 子目录（同名文件），
  并在说明文档顶部用醒目提示写清"根目录是核对版，投稿用子目录里的"。

## 六、用户说"只检查、不要改"时

原话："如果有的话，也不要做任何改动，而是详细告诉我，我决定是否手动改动。"
⇒ 纯只读审计：报告问题 + **位置**（段落号/文件）+ 建议改法，**一行都不动**。
列出的待办编号后，用户会用编号选（本轮"2、3、4、5"），此时**只改这几个编号**，
其余保持原样，并在回复里明确"第 1、6、7、8 项按你的选择未动"。

## 七、每次动手前先确认"当前文件状态"（用户会在两轮之间继续改文件）

用户**不会等你**。本轮真实发生：上一轮结论是"手稿末尾 Figure legends 整节被删"，
下一轮审计缩写时发现该文件 **mtime 已是当天 02:16**、段落数 **174 → 191**，
**legends 整节被恢复、还新增了 Supplementary Figure S1–S8 图注**——旧结论全部过时。

固定动作（读文件的第一件事）：
```python
st = os.stat(path); print(st.st_size, time.strftime("%m-%d %H:%M", time.localtime(st.st_mtime)))
print(len(doc.paragraphs))
```
1. 与上一轮的记录对照，不一致就**重新读一遍再下结论**，不要沿用旧快照。
2. **复检自己上次的修复是否存活**（本轮复核：4 处定点修复全部还在 → 可以放心在其之上继续改）。
3. 差异清单也要重出（`difflib` 对比"我的构建版 vs 用户当前版"），否则会漏掉用户新增的内容
   （本轮就是这样才看到用户自己把 Supplementary 图注贴进了手稿）。

⇒ 推论：**任何"缺什么/多什么"的判断都要现算**，包括字数、段落数、图注是否在手稿里、
哪些文件需要上传。审计类回答里凡是带数字的句子，都必须来自本次运行。

## 八、批量替换的四种翻车形态（每一种都真实发生过）

`str.replace` / 全局替换是这类任务引入新错的**头号来源**。四种形态：

1. **语义相反的两个语境共用一个数值** —— 为统一 L 层"关联样本"口径做 `2,056 → 2,092`，
   但同一数字在**"判别样本（腰围完整子集）"语境里也出现**，被一起改掉 →
   正文出现"判别样本 2,092 …… 比关联样本少 36 人"的**句内自相矛盾**。
   ⇒ 替换前列出**全部命中点并标注语境**，逐处判断；替换后回读每处。
   （这类错误还会在"从备份恢复"时**复发**——恢复点早于修复点，会把已修好的又带回来。）

2. **插入位置落在数字内部** —— 按"第一个句点"插入引用 → `0.826` 被切成 `0 (Table S11).826`；
   同类还出过 `age 26 (Figure S1).0/52.0/74.0`。
   ⇒ 用**完整锚点串**（整句或整短语）定位，不要用"第一个句点/空格"这种脆弱规则；
   插入后 grep `\(\d+\.\d+\)\.\d`、`\d\s*\(` 自查。

3. **只改半句** —— 同段前半句 `1.018/1.020 → 1.012/1.014`，后半句仍留
   `pooled fit 1.020 versus 0.990` → **段内自相矛盾**。
   ⇒ 一处修正要**整段回读**确认段内无旧值残留；把待改值按**段落**归档，改完按段核销。

4. **机械同义替换** —— `settled → addressed` 之类会命中不该改处、留下病句。
   ⇒ 替换后**逐处读整句**，不是只 grep 计数。

**通用防法**：每个替换 `assert OLD in text`（或打印 OK/MISS）；替换后**立即回读整段**；
把"位置 / 改前 / 改后 / 判据"记入变更清单（README 或 log），供用户复核与下轮回归检查。

## 九、构建链会随"直接改 docx"而失效（覆盖事故）

跨轮次**直接 patch 交付 docx** 之后，构建脚本与内容模块就与交付稿**脱钩**了。
真实事故：`_build_docx_v18.py` 依赖 `_ms_content_v18.py`，后者停在"打包前"状态
（摘要 342 词 / 8 表），而交付稿已被直接改成 299 词 / 7 表 →
**跑一次构建就把交付稿覆盖回旧版**（Table S13 消失、摘要膨胀、引用错位）。

**固定动作**：
1. 跑任何构建脚本前**先把交付稿复制进 `_bak/`**，并用 2–3 个**哨兵值**
   （摘要词数、表数、刚改过的某个数字）比对"内容模块 vs 交付稿"；
   **不同步就不要跑**，改走 §一 的 run 级定点 patch。
2. 交付目录留显式警告（README 顶部）："`_build_*.py` 已与交付稿不同步，
   除非要重建，否则不要运行"。
3. 把**重建顺序**写清：恢复备份 → 依次跑补丁脚本 → 跑校验脚本。
4. **清理构建链目录前先追 import 关系**：本轮归档 `_ms_content_v15/16/17.py` 后，
   `_ms_content_v18.py` 的 `import _ms_content_v17` 直接崩，构建链断掉。
   重建脚本链时把依赖模块一并放回。
