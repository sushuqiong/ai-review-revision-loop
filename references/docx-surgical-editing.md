# 程序化改 docx / 图的铁律（长期迭代项目反复踩坑所得）

适用：同一稿件 vN→vN+1 的多轮程序化编辑（python-docx 直接改 + 制图脚本重绘 + 重嵌）。

---

## 一、最高频错误：无判据的全局 find-replace

真实事故（同一项目内反复出现）：

1. **跨总体的数值被误改**：`2,056 → 2,092` 全局替换，把**判别样本**（腰围完整子集，本就应保持 2,056）
   也改成了**关联样本**数值 → 同一稿内两个样本混用，正文/表格/图互相打架。
   **该错误在同一项目出现 3 次**（引入 → 修复 → 从备份恢复时又被带回）。
2. **引用标记插进数字内部**：按"第一个句号"定位插入引用，落在小数里 ——
   `the M4 per-SD OR was 0.826` 变成 `was 0 (Table S11).826`。
   同类：`age 26 (Figure S1).0/52.0/74.0`、`weighted 2 (Figure S2).5%`、`P=0 (Figure S1).588`。
3. **只改半句**：段落前半改 1.012/1.014，后半仍留 `pooled fit 1.020 versus 0.990`
   → **段内自相矛盾**，被审查者一眼抓住。

**规则**

- **禁止** `str.replace(old, new)` 式的无判据全局替换。
- 改前先把该数值在**图/表/正文每一处的归属**列出来（同一数字可能同时属于两个不同总体）。
- 逐处改动必须输出清单：`位置 | 改前 | 改后 | 判据（为什么这里该改 / 不该改）`。
- 引用标记只在**句末**或完整从句之后插入；插完扫 `\d\s*\([A-Z]`、`\.\d` 确认未落进数字。
- 改一个数值后，**扫整段**找该量的所有旧变体 —— 包括**来自不同模型设定**的变体
  （例：数值 PIR 模型给 1.018/1.020，分类 PIR 模型给 1.012/1.014，两者同段并存即矛盾）。
- 若同一量存在多个设定，**先确定权威源文件**（哪个 `.txt` 是表的输出源），再全稿统一到它。

## 二、备份恢复会带回已修的错

从 `_bak/` 恢复交付稿后，**必须重跑该轮全部修复脚本**，不能假定备份是干净的。
（真实事故：恢复"打包前"备份后，已修好的判别样本 2,056 被覆盖回 2,092。）

## 三、构建链 vs 交付稿的漂移

- 交付稿常由**直接编辑 docx** 得到，而 `_ms_content_vN.py` 内容模块仍是旧版。
  再跑 `_build_docx_vN.py` 会**用旧版覆盖交付稿** —— 真实发生过：摘要从 299 词被写回 342 词、
  已移入补充材料的 Table 8 复活、表数从 7 变回 8。
- README 必须写明：「**除非要重建，不要运行 `_build_docx_vN.py`**」。
- 若要重建，顺序固定：`恢复备份 → 重跑打包脚本 → 重跑修正脚本 → 跑终验`。
- **验证脚本必须同时比对"全段落数"和"非空段数"**。只比非空段会永远输出 ✅，
  看不见空段膨胀/丢失（真实事故：重建稿 192 段 vs 交付 185 段，且**不幂等**，每轮 +7 空段）。

## 四、换 docx 内嵌图必须同步 extent

替换 `word/media/imageN.png` 后，`<wp:extent>` 与 `<a:ext>` 的 `cy` 必须按新图宽高比重算
（`cx` 保持不变），否则图被纵向拉伸。

- 改完核对：`cy/cx == 新 PNG 高/宽`
- md5 回读：嵌入内容 == 源 PNG 文件

## 五、批量编辑后的四项自检（每次必跑）

1. 各文件洁净度：中文 / 内部痕迹（`vN`、`_build`、`_ms_content`、`GPT`、`reviewer`、`01_数据`、`code/`）/ 占位符
2. **残留旧串计数**（应全为 0）
3. **新值存在性**（应全为 1+）
4. 表内数值与正文数值一致性

输出 `未通过项: N`，逐项归零或如实说明；**不允许只报"已完成"而不带这个计数**。

## 六、派 subagent 改图/改档的任务粒度

- 两次派「重绘 6 图 + 生成 legends + 重嵌 docx」这种**大任务**，都在迭代上限内耗尽且**零交付**。
- 拆成**极窄单产出**任务后立刻成功：
  - ✅「只补完 `_make_figs_v19.py` 末尾 20 行并运行」→ 3 张主图产出
  - ✅「只改写 `_make_supp_figs_v19.py` 的三个 builder 并运行」→ 3 张补充图产出
- **规则：一个 subagent 任务 = 一个可验证产出。** 图件类任务按"每组图一个任务"拆；
  docx 重嵌 / legends 生成 / 清理归档由主 agent 自己做或另起小任务。
- 派图件任务时 context 必须给全：
  1. **权威源脚本路径** —— 且派发前**自己先核验它能否逐位复现当前图**（脚本可能已过时：本项目
     `_make_figs_v16.py` 仍印旧口径 `2021–August 2023 / incl. waist / 2,057`，与 v19 不符）
  2. 逐字列出**要移除**与**要保留**的元素（保留项要说明判据：凡与坐标轴/数据元素绑定的文字保留）
  3. 交付规格：宽 / 最小字号 / PDF Type3=0 / 四边留白 > 0 / 重叠 0
  4. 红线：**严禁改数据、坐标、几何；严禁截图代替矢量重绘**
- 要求 subagent 在动手前**先做数据一致性核对**（如像素级 diff 证明源脚本产出与现图逐位一致），
  再授权修改。

## 七、图内文字移除的安全做法

- 用**纵向裁切框架**：pass1 在 reference 画布量 ink 上下沿 → pass2 以 `PAD≈0.07 in` 重画，
  **宽度恒定**，数据坐标逐位不变。
- 交付前用**像素级比对**证明几何不变：重叠区 `|Δ|≤2` 像素占比、纵向子带最佳平移是否为纯平移
  `dy`（无缩放）、面板矩形英寸坐标偏差是否为 0。
- 断言必须成对：**"已移除断言（残留=0）"** + **"已保留断言（数据元素仍在）"**。
- 只删 `fig.legends`，**不要**误删轴内同名文字（真实陷阱：三行 cohort 名同时是底部图例键
  和左侧行分组表头，前者删、后者必须留）。
- 图内 <8 pt 的字号要分清是"正文级文字"还是"设计内小注"（面板小注、mathtext 角标）；
  后者在基线版本里就等于 7.0 pt / 5.6 pt，属沿用而非回退。

## 八、插入 / 重排章节：`addprevious()` 的锚点陷阱（本会话真实踩中，由用户发现）

增补新章节时**最容易错的不是内容而是锚点**，而且错完之后文档能正常打开、表面看像正常排版，
**只有逐段读才会发现**。本次一次全中三种症状：

| 症状 | 成因 |
|---|---|
| 新章节**标题排在它自己正文的后面** | 先插正文（`body.addprevious(para)`）、再插标题（`heading.addprevious(para)`），标题落到正文之后 |
| **章节顺序颠倒**（2.9 出现在 2.8 之前） | 多个 `addprevious()` 锚定到**同一个**锚点，先后插入的元素顺序被反转 |
| **编号冲突**（出现两个 "3.9"） | 新增章节自带编号，与既有编号撞车（原 3.9 = IPW 敏感性，新增的"时间验证"也编 3.9） |

**正确做法**

1. 先按目标顺序组装**完整块**（标题 + 正文 + 表注），一次性插入到**明确的锚点之前**：
   ```python
   for el in reversed(block):      # reversed 保证块内顺序不被反转
       anchor.addprevious(el)
   ```
2. 或插入后做一次"**标题归位**"：把每个 `N.M 标题` 段落移到**它自己正文段**之前：
   ```python
   body.remove(heading); body_para.addprevious(heading)
   ```
3. **新增章节后必须重排整章编号**，并保证**连续**（1..N，无重复、无跳号）。
   重编号时按"出现顺序"统一重排，而不是只改新增的那几个。

**必跑的结构自检（三问，每轮改稿都跑）**

```
① 每个 "N.M 标题" 的下一段是否为正文（而不是另一个标题）？
② 各章编号是否连续（方法 2.x / 结果 3.x，无重复、无跳号）？
③ 正文里所有 "Section X.Y" 引用是否仍指向存在的章节？
```

第 ③ 问最易漏：**重编号后不核查交叉引用 = 引用指向错误章节**。
（本项目重编号后核查：所有 `Section 2.4/2.5/2.7/3.1/3.3/3.7/3.8/4.x` 都落在未变动的编号上 → 安全；
新增章节暂无正文引用指向，亦无悬空。核查脚本：`re.findall(r'Section\s+(\d+(?:\.\d+)?)', full)` 再去重排序。）

## 九、表格格式判定：三线表 vs 网格表（不要只看样式名）

**判定标准**

- **合格三线表** = 表级 `w:tblBorders` **全为 `none`/`nil`**，实线写在**单元格级 `w:tcBorders`**：
  首行 top 粗线（sz 12）+ bottom 细线（sz 6）；末行 bottom 粗线；**左右为 `nil`、行间无线**。
- **不合格** = `tblStyle` 为 **`Table Grid`（style 值 35）**，或表级边框出现 `val="single"` → 会有**竖线与行间网格**。
- 合格表用 `style=12` 或 `style=9` 都可以 —— **关键是边框落在哪一层、有没有竖线**，
  所以校验脚本必须读 `tblBorders` 的**值**（不只看节点是否存在），并遍历 `tcBorders` 的 left/right。

**常见事故**：`doc.add_table(...); t.style = "Table Grid"` → 直接产出网格表。
本次新增的 3 张补充表就是这样写坏的（另有 5 张旧表带表级边框）。

**新建表一步到位写成三线表**：设 `tblStyle=12` → 删表级 `tblBorders` → 逐单元格写 `tcBorders`（左右 `nil`）。
**批量修表**后**再跑一次校验**，输出"有实际边框的表数 / 有竖线的表数"，两者都应为 0。

## 十、跨文件数值漂移：交付前必查清单

一轮改动（换期刊 / 改标题 / 重算分析 / 改措辞）之后，**同一批数字与表述散落在多个文件里**，
改了一处必漏另一处。交付前逐项核对：

| 漂移项 | 常见落点 | 本次实例 |
|---|---|---|
| 标题 / running title | 主稿、Title page、Cover letter、STROBE、补充材料首页 | running title 仍是旧版 |
| 摘要 / 正文词数 | Title page 的统计段 | 仍写 350 词，实测 341 |
| Supplementary 编号范围 | Title page、主稿说明段、补充材料首页 | 仍写 "Tables S1–S13"，实际到 S16 |
| Highlights 条数与长度 | Highlights | 7 条（期刊惯例 3–5 条），其中 2 条 >250 字符 |
| **分析框架表述** | Cover letter vs 主稿 | Cover letter 写"两期为主分析"，但最终决定保留三时期框架 |
| 结局 / 变量措辞 | 主稿正文、**图内文字**、补充材料、Title page | 旧结局措辞残留 |

**表 / 图分节顺序**（用户明确要求）：补充材料里 **所有表在前、所有图在后**，不得交错。
检查法：遍历 body 顺序，确认所有 `Table SN` 标题都排在第一个 `Figure SN` 标题之前；
新增表若被追加到文末（图之后），必须整块前移。

**回查方式**：程序化改稿里 Word 的"查找"不可靠 —— 用脚本对**全文（段落 + 表格单元格 + 图内 PDF 文本）**
做计数式核对：**旧串计数应为 0、新串应 ≥1**，并输出计数（不允许只报"已完成"）。

## 十一、修"疑似笔误"前先核实该变量是否真实存在

真实教训：图内出现 `HAJ0 age-branch outcome`，看起来像笔误（外部 AI 也判定"很可能是笔误"）。
核查**数据构建脚本**后发现：**HAJ0 是 NHANES III 的真实变量**（Section J 年龄分支指示：1=17–74 y，2=≥75 y），
补充材料里 `keyed on the HAJ0 age branch` 是**准确描述**；真正错的是**图内把 HAJ0 当成了 outcome**
（实测应为 HAJ9/HAJ12/HAJ16/HAJ17）。

**规则**：遇到疑似变量名笔误，先去**数据构建脚本 / 代码本**确认该名字是否真实存在，再决定改不改。
凭"看起来像笔误"直接改，会把正确表述改错（本次若照改，7 处正确描述会被误伤）。
