# 三路冷读审稿协议（独立 subagent 并列冷读）

来源：2026-09 EGFR 跨疾病资源 v13（作者已自审 8+ 轮、历轮 20+ 条意见全部闭环之后）。**3 名互不知情、上下文全新**的 subagent 仍报出 25+ 条实证问题，其中 6 条 Blocker（含作者多轮未发现的“取中位不排序”错误）。
结论：**自审不能替代冷读**；“上一轮意见已闭环”≠“没问题了”。

## 何时用
- 宣布“可以投稿了”之前；外部 AI（GPT6/Claude）意见已逐条闭环之后；
- 交付物跨多个文件类型（正文/表/图/数据包/ZIP/文档）时——跨文件漂移只有换视角才看得见。

## 派发方式（delegate_task 批量，3 个并行）
职责切分（不同 mandate 才会看到不同东西）：

| 角色 | 盯什么 |
|---|---|
| **编辑合规审稿人** | 期刊硬性约束（字符/词数/章节/许可/DOI/仓库名）、正文承诺 vs 交付物清单、图注与图是否对应、表是否三线表、图表尺寸与单页上限、元数据与正文数字是否同口径 |
| **统计/方法审稿人** | 效应量与方差定义、配对/非配对混合池化的权重与可解释性、多重检验 family、共线性与耦合（VIF vs R²）、协变量共享基因、生殖/敏感性分析是否被当成主结论、措辞是否超出证据等级 |
| **数据工程/可复现审稿人** | 实际跑校验（`sha256sum -c`）、跑示例并 diff expected_output、ZIP 与清单一致性、包自足性（点名文件是否存在）、脚本路径/依赖、编码/换行、join key 是否真给、文档-实现一致性 |

## 指令模板（每条都关键，缺一条就会得到“看起来没问题”式的空报告）
```
环境/路径：<绝对路径列表：正文 md/docx、表 docx、图目录、数据包、ZIP、脚本目录>
可以：读文件、跑只读命令（python/R 读 CSV；docx 用 python-docx；可在临时目录解压 ZIP 副本）
禁止：修改任何交付文件、git 操作、联网写
已知并已披露的局限（不要作为新问题重复报告）：<逐条列出，如单作者无实验、某数据集整层排除、某模块不可重算、N 个队列无患者标识、两分数共享基因、仅秩一致、DOI 占位符>
输出格式：按 Blocker / Major / Minor / Suggestion 分组，每条含
  ① 问题陈述 ② 证据（文件路径 + 原文/数值/命令输出）③ 建议改法 ④ 能否用现有数据立即验证
若某处没问题，必须写明“检查了什么、怎么查的”（禁止“看起来没问题”）
不要复述稿件内容；用中文回答
```

## 汇总与处置纪律（收到报告后）
1. **逐条自己复核**再动手：三份报告里也有误判（例：编辑审稿人按旧状态文档判定“仓库未改名”，实际已执行 → 修的是状态文档而非重做改名）。
2. 按 Blocker → Major → Minor 修；每条在 `06_三路冷读审稿意见与处置_vN.md` 写明「意见 / 我的复核 / 处置」，**未采纳也要写理由**。
3. 修完必做回归：主审计 + 对抗自查 + `sha256sum -c` + 图件 OCR 版面 + 示例实跑（改动会牵连别的断言——实例：拆图后“图表数量=3”的断言必须同步改）。
4. 把冷读报告与处置文档一起进包、进 ZIP、推 GitHub：下一位审稿人能看到问题闭环史。

## 高命中率检查点（本轮实际被抓到的，按性价比排序）
- 同一实体在两个随包文件里数值矛盾（TP53 86/96 vs 156/185）→ 交叉核对所有含同一量的表。
- 校验文件自引用陈旧哈希 → `sha256sum -c` 实测一次（别假设）。
- 声明的示例不可运行 / expected_output 与实际脚本不同源 → 真跑一次。
- 正文数字与 README / Zenodo 指南 / 变更日志口径不一致 → 三处以上同量比对。
- 图高（不只是宽）与单页上限；图形文字的“最小字号”是否达标。
- 正文声称已联网核验，而随包 QC 文件记录的是失败/陈旧结果 → 核验证据文件必须与声明同源、同时点。

## 第二轮（v13→v14）新增经验：冷读 + 外部 AI 复审交替，命中点在“漂移”
同一份交付物连做两轮后，**问题类型会整体换挡**——第一轮抓错值与断链，第二轮抓“结构合规但内容不完备”。据此调整 mandate 与检查点：

1. **给每轮定主题**：第一轮 = 数值/校验/示例（工程与统计）；第二轮 = 内容完备性（参考文献、检索流程、QC、字典、本体、替代方法）+ 图文一致性（图注与面板、图号顺序、docx 是否嵌入全部图）。
   - v13→v14 实测：外部 AI 报 17 条，3 条“最高”全部是**呈现层**（Figure 4 未嵌入 docx、标签重叠、无参考文献列表），而非数据错误 → 别再只盯着数字。
2. **必须在派发前刷新“状态文档”**：本轮一位审稿人按旧状态文档判定“仓库尚未改名”（实际已执行），属**假阳性来自陈旧上下文**。规则：状态/待办文档先更新，再派冷读；或在指令里写明“状态文档可能滞后，以文件系统实测为准”。
3. **要求审稿人自证“查过哪些点、怎么查的”**（模板已含）。本轮三份报告都附了“已核对无误”清单与所用命令/复算片段，可直接用作**交叉验证证据**写进处置文档。
4. **建议每位审稿人复算一处关键统计**（本轮一位用 Python 自实现 REML+Hartung-Knapp，逐位复现 pooled est/se/p）——比“读表核对”更有说服力，也顺手验证了主管线。
5. **汇总纪律再加两条**：
   - 审稿人给的“正确值”也要核（本轮有把 20,451 写成 29,451 的笔误，方向与结论一致但数字需以随包 CSV 为准）；
   - 声称“正文数字不符”时，先定位**唯一权威来源**（冻结 CSV），再判定是正文错、表错还是生成器错——本轮 3 处中有 1 处根因是生成器 `x[len(x)//2]` 未排序。
6. **回归清单随版本增长**：每修一类问题，就把它的检查写进审计脚本（本轮新增：TP53 必须 86/96、442 行矩阵、四图被引用、References 存在、`sha256sum -c` 无告警）。下一版审计条目只会更多，不会更少——这正是“每轮都能再抓到东西”的机制。
